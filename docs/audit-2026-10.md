## What was done

- Copied the repo to the Extreme SSD and installed the pinned `requirements.txt` into a fresh `.venv` (Python 3.12, Apple Silicon).
- Imported and launched the app, then ran `scripts/full_smoke_test.py` end to end.
- Four parallel code reviews covered:
  - the UI (`app.py`, `ui/`)
  - ML (`training/`, `models/`, `modalities/`, `eval/`, `detection/`)
  - data and export (`data_pipeline/`, `export/`)
  - release (`runtime/`, `packaging/`, CI, dependencies)
- Spot-checked the most serious claims against the code or by running it.

Each finding is tagged:

- **Verified:** I reproduced it or confirmed it in the code myself.
- **Reported:** found by a review and not yet reproduced.
- **Inferred:** reasoned from the code but not tested.

## Headline

**The app installs, launches and passes its smoke test today.** The pinned dependencies still resolve on Python 3.12 arm64, and every modality trains and exports a bundle.

**Passing the smoke test doesn't mean the results are correct.** The smoke test only checks that each step returns, not that the results are right. Behind that green run are:

- several bugs that quietly corrupt training data or metrics
- an exported serving path that only works correctly for image models
- a macOS launcher that crashes in any build made from the current code
- a dependency set (Gradio 4, Starlette 0.38, Pillow 10) with known CVEs that can't be patched without a Gradio upgrade

## Recommended plan

Work through the phases in order. Each phase makes the next one safer.

### Phase 0: Safety net (do first, about a day)

1. Make `scripts/full_smoke_test.py` **assert**: fail on any `❌`, "Evaluation error", empty bundle or exception text in a result.
2. Add a CI job (macos-14 arm64 and windows-latest, Python 3.12) that:
   - installs `requirements.txt`
   - runs `run_local.py --smoke-test`
   - runs the smoke test with the default `num_workers`
3. Fix the security-scan paths, drop `continue-on-error`, and use `shell: bash` (which enables pipefail).
4. Add a small pytest suite for the pure functions behind V2–V4, the cleaning step and type inference. These are cheap to test and regress silently.
5. Add one `set_seed()` that seeds torch, numpy, random and the DataLoader generators. `DEFAULTS["seed"]` exists but is never used.

### Phase 2: Exports that actually serve (Reported)

The FastAPI and Docker export is only correct for image models today.

- **Tabular, time-series and text:** the server skips the training preprocessing (scaling, one-hot encoding, lag features, the tokenizer regex), so predictions are confidently wrong. Generate a `preprocess()` from `preprocessing.json`, plus a parity test that compares server output with training output.
- **Audio:** the export routes to the image endpoint and is missing Pillow, so it can't be served.
- **Transformer text:** the ONNX model needs `attention_mask` too, and the export doesn't use the tokenizer.
- **sklearn ONNX:** the server crashes on the 1-D label output. Convert with `zipmap=False` and read `probabilities`.
- **Regression:** softmax and argmax are applied to regression output.
- **Docker export:** depends on FastAPI export having run first.
- **Generated servers:** bind `0.0.0.0` with no auth, and leak raw exception text.
- **Generated requirements:** unpinned, and the Streamlit dashboard uses `use_container_width` (removed upstream).
- **Model selection:** the exported dashboard ranks regression runs backwards.

### Phase 4: Dependency upgrade (security)

- **Gradio 4.44.1 is end-of-life**, with advisories fixed only in 5.x. Moving to Gradio 5 also unlocks:
  - Starlette ≥0.49.1 (CVE-2024-47874, CVE-2025-54121, CVE-2025-62727)
  - Pillow ≥12.2 (2026 out-of-bounds write CVEs; Gradio 4 pins `pillow<11`)
- Disable analytics with `GRADIO_ANALYTICS_ENABLED=False` (V6).
- Gradio 5 migration points in `app.py`:
  - the private `_frontend=` launch kwarg
  - the monkeypatched `gradio_client.utils._json_schema_to_python_type`
  - `gr.Dataframe(height=)`
  - stricter file serving: set `allowed_paths`, which also fixes annotation previews today
- After the upgrade, generate a `uv` lock file with hashes.
- Deprecations to fix while you're there:
  - `torch.cuda.amp.GradScaler`
  - `torchaudio.load`, which needs torchcodec from 2.9
  - timm head-swapping
  - pandas 3 string dtype handling in type inference

### Phase 5: Structure and UX

- **Split `app.py`** (7,340 lines). It holds about 1,340 lines of inline CSS, a 1,240-line `run_pipeline` generator with about 75 positional parameters (copied by hand in five places), and about 2,500 lines of callbacks. Suggested layout:
  - `styles/app.css`
  - `pipeline/orchestrator.py`, with load, build, train, evaluate and export stages that raise on failure
  - a `RunConfig` dataclass
  - `ui/layout.py`
  - `ui/callbacks/*.py`
- **Cancellation and concurrency:**
  - Stop only takes effect at the next `yield`.
  - Cross-validation, sweep, hparam search and YOLO jobs can't be cancelled.
  - There's no shared GPU concurrency limit.
  - Use a worker thread with a stop `Event` and one `concurrency_id`.
- **Shared state:**
  - `project_state.json` is read-modify-written without a lock, and one writer erases other keys.
  - One named pyplot figure is shared across threads.
  - Figures are never closed, so memory grows.
  - Temp CSVs and zip extractions are only cleaned up at exit.
- **Annotation tools:**
  - The YOLO review numbers classes per image, which corrupts the dataset.
  - Relabeling rewrites the user's source CSV with no backup.
  - Folder relabels accept `../` paths.
- **Data handling:**
  - No CSV delimiter sniffing (semicolon files load as one column).
  - The "id" substring rule drops `humidity` and `width`.
  - The quality report says "Ready" for blocking `❌` errors.
  - Integer column names crash type inference.
  - Zip uploads have no size or file-count limit.
- **Unsafe deserialization:** `torch.load(weights_only=False)` and `joblib.load` run on bundles the user opens. Warn the user, or use `weights_only=True` or safetensors.
- **Dead code:** `wrap_pipeline_error`, `format_hyperparams`, `estimate_training_time`, `load_bundle`, and the stale "22-tuple" comment.

## Suggested order of work

1. Phase 0, then Phase 1's critical rows. These are small diffs, and the new tests protect them.
2. Phase 3's four critical installer bugs, before cutting any new release.
3. Phase 4 (Gradio 5), using the Phase 0 CI as the regression gate.
4. Phase 2 exports, then the Phase 5 refactor. Do the refactor last, once tests exist.
